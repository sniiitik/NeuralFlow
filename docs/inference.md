# Phase 3 inference

## Architecture

The Next.js control plane owns PostgreSQL registry/deployment records and verifies artifact checksums from local storage. Its `/api/inference/*` gateway sends a checked JSON artifact and typed Iris measurements to a private FastAPI runtime. The runtime validates the artifact again, caches each immutable version by version ID and checksum, and executes multinomial logistic regression with a softmax probability output. It has no database credentials, filesystem artifact access, pickle loader, or code execution path. A runtime restart clears only its cache; the next prediction reloads the registered artifact through the gateway.

Only `sklearn_iris_logistic_regression` JSON schema version 1 is executable. The artifact contains four named Iris input features, three named classes, a 3 by 4 coefficient matrix, three intercepts, four scaler means, and four positive scaler scales. The values are exported from a real scikit-learn `StandardScaler` and `LogisticRegression` pipeline. The runtime computes `(input - mean) / scale`, then class scores, softmax probabilities, and the highest-scoring class. No serialized Python objects are accepted.

The runtime service in Compose has no public interface. Its optional host mapping is `127.0.0.1:8001:8000`, and the Compose app reaches it at `http://inference:8000`. For local `npm run dev`, set `INFERENCE_RUNTIME_URL=http://127.0.0.1:8001` (the default). Runtimes require `INFERENCE_RUNTIME_TOKEN` on non-health paths; the gateway and registry require a Better Auth session and appropriate role.

## Reproduce the Iris demo

First start PostgreSQL and apply migrations as described in the README. Build and start only the private inference service:

```bash
docker compose --profile inference up -d --build inference
curl http://127.0.0.1:8001/healthz
curl http://127.0.0.1:8001/readyz
npm run dev
```

Train two versions with scikit-learn 1.6.1 in the pinned Python 3.11 trainer image. This writes `var/trained/iris-v1.json` and `var/trained/iris-v2.json`; the script prints held-out accuracy and SHA-256 for each. The checked-in `inference/examples` files were generated by the same script.

```bash
docker compose --profile train run --rm --build trainer
```

Register the artifacts under one family. These commands require `jq` and assume this is a new family; use a new family name or version if you have already registered them.

```bash
V1_ID=$(curl -fsS -X POST http://localhost:3000/api/models \
  -F name=iris-classifier -F version=v1 -F framework=sklearn -F owner=NeuralFlow \
  -F artifact=@var/trained/iris-v1.json | jq -r '.model.id')
V2_ID=$(curl -fsS -X POST http://localhost:3000/api/models \
  -F name=iris-classifier -F version=v2 -F framework=sklearn -F owner=NeuralFlow \
  -F artifact=@var/trained/iris-v2.json | jq -r '.model.id')
```

Activate either or both versions. Activation validates and loads the artifact in the runtime before committing a completed inference deployment to PostgreSQL. Repeating activation for an existing version returns its existing deployment. The playground shows these deployments at `/inference`.

```bash
V1_DEPLOYMENT=$(curl -fsS -X POST http://localhost:3000/api/inference/deployments \
  -H 'Content-Type: application/json' -d "{\"versionId\":\"$V1_ID\"}" | jq -r '.deploymentId')
V2_DEPLOYMENT=$(curl -fsS -X POST http://localhost:3000/api/inference/deployments \
  -H 'Content-Type: application/json' -d "{\"versionId\":\"$V2_ID\"}" | jq -r '.deploymentId')
```

Predict from a deployed version:

```bash
curl -fsS -X POST http://localhost:3000/api/inference/predict \
  -H 'Content-Type: application/json' \
  -d "{\"deploymentId\":\"$V1_DEPLOYMENT\",\"features\":{\"sepal_length\":5.1,\"sepal_width\":3.5,\"petal_length\":1.4,\"petal_width\":0.2}}"
```

The result includes `prediction`, `probabilities`, `modelVersion`, `modelVersionId`, `inferenceMs`, and `requestId`. Use `V2_DEPLOYMENT` to request the second trained version explicitly.

## API contract

| Endpoint | Purpose |
| --- | --- |
| `GET /healthz` and `GET /readyz` on the private runtime | Process health and ability to load/serve artifacts; readiness includes cached version count |
| `POST /v1/models/load` on the private runtime | Validate and cache an artifact by version ID and checksum |
| `POST /v1/predict` on the private runtime | Validate input and execute model math |
| `GET /api/inference/deployments` | List active deployments with supported sklearn JSON artifacts for the playground |
| `POST /api/inference/deployments` | Activate `{ "versionId": "..." }` after a successful runtime load |
| `POST /api/inference/predict` | Accept `{ "deploymentId": "...", "features": { ... } }` and forward to the target version |

The four feature keys are `sepal_length`, `sepal_width`, `petal_length`, and `petal_width`, measured in centimeters. Each must be a finite number greater than zero and at most 20. Invalid gateway payloads return 400, unavailable deployments return 404, incompatible artifacts return 415 or 422, and an unavailable runtime returns 503 or 504. The runtime uses 422 for malformed requests or artifacts and includes a request ID. `X-Request-ID` can be supplied to correlate a prediction; otherwise the gateway generates one.

## Tests

```bash
docker build --target test -t neuralflow-inference-test ./inference
docker run --rm neuralflow-inference-test
TEST_DATABASE_URL='postgresql://neuralflow:neuralflow@localhost:5432/neuralflow_phase2_test' npm run test:inference
```

The Node test uses a separate migrated `_test` database and a temporary artifact directory. It requires the loopback runtime to be running. It registers both checked-in trained artifacts, activates both versions, predicts real Iris inputs, and checks invalid requests.

## Current limits

Family inference follows the durable serving route across two fixed runtime slots; see [routing.md](routing.md). Direct prediction by an activated deployment ID remains available. Shadow deployments mirror bounded requests while returning only the stable response. Only the exported Iris logistic-regression JSON schema is executable; other registered JSON and safetensors artifacts remain inert. Each runtime has an in-memory cache, and the gateway transfers the checked artifact on each request, so large-scale serving needs a different loading protocol. The system does not yet provide distributed quotas, autoscaling, or general model serving.
